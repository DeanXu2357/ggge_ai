## 2. 用語（暫定，定案後再決定是否進 terminology-map）

| 用語 | 意義 |
|---|---|
| 主迴圈 | 只負責 UI 操作的最外層迴圈：觀測、取得決策、操作、驗證 |
| UI sim engine | UI 的模型：UI 狀態、每個操作的預期結果與期限、操作能取得的資訊 |
| 建模引擎 | 讓主迴圈理解「操作的意義」的領域模型的總稱；battle engine 與觀察引擎都屬於這一類 |
| battle engine | 既有的 Go 戰鬥引擎（`engine/`） |
| 觀察引擎 | 建立地圖資訊、並評分掃描狀態的引擎；不碰 I/O |
| 意圖 | 建模引擎輸出的領域層要求（例：「探 (12,7)」「A 機移動到 (5,3)」），不是手勢 |
| 手勢 | 打到裝置上的單一 tap／swipe／key |
| 畫面判讀器 | 幀的唯一消費者：辨識當前畫面、核對當前幀上的事實、判斷靜止與位移。不叫「量測」，那個詞與 metric 相近，會讓職責偏移 |

## 4. 現況調查結論

調查對象：`scripts/sweep_scan.py`（1819 行）與其依賴。

### 4.1 遊戲與裝置本身造成的問題（任何實作都要面對）

1. 狀態只能從像素推得。
2. 送出的手勢不一定生效（省電觸控鎖、系統鎖無聲吞掉）。
3. 轉場與動畫期間的幀不能當判定依據；地圖有常駐待機動畫。
4. 同一座標在不同畫面是不同的鈕，部分誤點無法復原。
5. 地圖鏡位沒有絕對讀數；推鏡會被邊界夾停。
6. 點擊格子有副作用（我方：選擇態＋置中；敵方：出卡）。
7. 轉場時間長短不定（開場運鏡約 15 秒、下載對話框最長 60 秒）。

### 4.2 實作方法造成的問題

1. 等待時間以「輪次 × 截圖延遲」隱含表達；81 處固定 sleep。
2. 幀沒有時間戳，「幀晚於手勢」只能靠 sleep 擔保。
3. 危險帶放在看不見畫面名的裝置層，以座標黑名單表達，帶與帶互相衝突。
4. 每個模組各自實作「等畫面停下來」。
5. `SweepRun` 單一類別持有約 40 個可變欄位，I/O 時序與領域邏輯無法分開
   測試。
6. `runtime/` 不得 import `battle/` 的分包規則，迫使腳本層注入。

### 4.3 歸類未定

1. ［假說］鏡位定位機制（標記搬運、信任節點鏈、回退、重錨、三條活鎖
   保險絲）的複雜度，大部分來自「只比對推鏡前後兩張幀」造成的格距取模
   歧義。串流逐幀累加位移可以消除歧義。
2. ［假說］`input swipe` 放手帶慣性造成行程不確定；改用按住、移動、
   停住、放開的觸控序列可以讓行程可重現。

### 4.4 舊版（0807 刪除）失敗的位置

迴圈骨架（sense → plan → act → verify、以畫面證據推進佇列）舊版已經有，
失敗不在骨架：

1. 模型粒度是假的：GOAP 動作宣告一條畫面邊，`execute()` 內卻是多次點擊、
   輪詢、彈窗處理；整場戰鬥是單一動作。
2. 效果宣告成單一確定值，表達不了結果集合與插入的彈窗。
3. 期限散寫在各 `execute()`，不在模型裡。
4. UI 狀態只有畫面名。
5. 刪掉的 28.8k 行絕大部分是「從像素讀出戰場狀態與鏡位」，這件事沒有
   完成。

## 5. 已談定的架構

### 5.1 主迴圈的五個步驟 ［確認］

1. 觀測當下。
2. 使用引擎決策要做的操作，以及預期進入的 UI 結果與驗證期限。
3. 操作前重新截圖，確認畫面仍是步驟 1、2 觀測時的畫面，才操作。
4. 檢查操作之後的畫面是否符合 UI sim engine 的預期。
5. 檢查操作之後的領域狀態是否符合建模引擎的預期。

核心改變：操作不是「做完再觀測狀態」，而是「先預測狀態，再驗證預測」。

### 5.2 UI sim engine ［確認］

- 所有 UI 操作邏輯都建在這裡：哪個畫面可以進到哪裡、每個操作能取得
  什麼資訊。
- 狀態範圍包含戰鬥地圖的鏡位與選擇態（不只是離散畫面）。
- 不再區分「關卡前用一種演算法、關卡內用另一種」。主迴圈第一層的決策
  一律用 UI sim engine 探索怎麼操作。
- ［提案］UI 狀態＝畫面名＋覆蓋層（卡條、卡片、對話框）＋地圖模式
  （hub／選擇態／武裝選擇）＋鏡位估計值（帶容差的連續量）。
- ［確認］操作的預期是「結果集合＋期限」，不是單一值。
- ［確認］一個迴圈週期只做一次操作，操作內部沒有觀測。手勢可以
  有內部時序（swipe 的持續時間、按住—移動—停住—放開、雙指縮放），那是
  裝置層的資料，不是操作邏輯；但手勢與手勢之間一律隔著一次判讀。
  使用者的疑慮：這是否能滿足不同取樣間隔。分析見 §5.3.7。

### 5.3 建模引擎與決策 ［確認方向，細節未定］

- 主迴圈的決策結合多個建模引擎來理解操作的意義，再回饋做決策。
- 觀察引擎的邏輯獨立於 UI 操作與主迴圈之外。
- ［提案］建模引擎輸出意圖；UI sim engine 把意圖分解成本週期要做的
  那一個手勢。
- ［撤回 2026-09-22］原提案「建模引擎對 UI sim engine 提供
  `occupant(cell)` 查詢」不採用。點格的流程見 §5.10；UI sim engine 不
  需要知道格上是誰。

### 5.3.1 物件清單（使用者列舉，2026-09-21） ［確認］

意圖這一層沒有被省略；要有哪些物件仍在探索中。

既有或已談定的建模：

| 物件 | 是系統對什麼的理解 |
|---|---|
| battle engine | 戰場與遊戲規則 |
| UI sim engine | 操作介面與流程 |
| 觀察引擎（Observer engine） | 怎麼探索地圖、怎麼評分一張地圖 |

目前缺少的邏輯：

1. 養成的建模：系統對局外養成的理解。
2. 隊伍評估：組合持有的資源與 battle engine 的搜尋，組出勝率最高的
   隊伍。
3. 戰鬥評估：關卡戰鬥時評估 battle engine 的內容，搜尋勝率最高的策略，
   再把策略交給操作邏輯，做成可實際執行的操作。
4. agent：操作的邏輯。依據 UI sim engine 的反饋、各階段建模引擎與
   評估器的建議，在主迴圈決定行動。

更正 §5.3 的提案：建模引擎本身不輸出意圖。意圖來自評估器對建模引擎的
搜尋結果；由誰把意圖轉成操作，見上面第 3、4 項。

### 5.3.2 三種職責：建模／評分／搜尋 ［確認］

§5.3.1 的「評估」拆成兩個職責，用語從此分開：

| 職責 | 輸入 → 輸出 |
|---|---|
| 建模 | 狀態＋意圖 → 之後的狀態（可能是多個分支） |
| 評分 | 一個狀態 → 一個分數。不搜尋、不提建議 |
| 搜尋 | 當前狀態＋建模＋評分 → 建議的下一個意圖 |

「策略」是搜尋的輸出，不是評分的輸出。

各領域的對應：

| 領域 | 建模 | 評分 | 搜尋的輸出 |
|---|---|---|---|
| 戰鬥 | battle engine | 勝率／目標達成度 | 下一個戰鬥意圖 |
| 觀察 | 地圖知識（已知與未知的格、台數帳） | 地圖完整度 | 下一個探測意圖 |
| 隊伍 | 無或極薄（見下） | 重用戰鬥的評分 | 隊伍編成 |
| 養成 | 養成建模 | 未定 | 未定 |
| 操作 | UI sim engine | 操作成本（手勢數、時間、風險） | 下一個手勢 |

- ［確認］觀察引擎拆成「地圖知識（建模）」與其上的評分、搜尋。地圖知識
  就是 battle engine 開局盤面的未完成版本，建完後交給 battle engine。
- ［確認］隊伍這一列是編排其他建模與評分的邏輯，不是平行的第五組：
  1. 拿關卡資訊帶入 battle engine。
  2. 用關卡規則（出擊場地、出擊 tag 限制）與實際持有的資源，產生合法的
     候選隊伍。
  3. 用戰鬥的搜尋與評分算出每個候選隊伍的結果，加上自己的搜尋找出最佳
     組合。
- ［提案］搜尋的輸出＝意圖＋價值＋預期結果集合；只輸出下一個意圖，
  每週期重新計算，agent 不保留計畫佇列。
- ［提案］agent 的職責：依 UI 情境決定聽哪個領域的搜尋；把意圖交給操作
  搜尋取得一個手勢；執行 §5.1 的五個步驟與 §5.4 的三分類。

### 5.3.3 agent 的仲裁規則 ［確認］

- 前期採用有序規則表（§8 第 1 項的乙）：每週期由上往下檢查，第一條
  成立的規則決定由哪個領域出意圖。agent 不保留計畫狀態。
- 使用者偏好的長期方向是目標堆疊（丙），因為它可以拆分子計畫。前期先用
  乙做出簡單結果，再決定改進方向。
- 為了日後能轉成丙，每條規則寫成三個欄位：**目標名稱**、**目標已達成
  的條件**、**目標未達成時由哪個領域出意圖**。轉成丙時只需要補上目標
  之間的父子關係，規則本身不必重寫。

### 5.3.4 畫面判讀器 ［確認］

- 畫面判讀器是單獨的物件：取得當前畫面，回傳當前畫面的解釋。UI sim engine
  在意的是畫面的流轉，不接觸幀。
- 比較「預期」與「實際」的編排邏輯由 agent 負責，不在畫面判讀器內，也
  不在 UI sim engine 內。
- 畫面判讀器不依賴任何建模。它用自己的詞彙（畫面空間的事實）描述幀；
  怎麼使用這份解釋是 agent 的事。
- 提供兩種詢問，兩種都只針對當前幀：
  - 辨識：這一幀是什麼畫面、上面有什麼（開放式）。
  - 核對：這一幀上某個事實是否成立（輸入是要核對的事實）。
- 核對不得被要求回答當前幀上沒有的資訊（例：在組隊畫面核對敵人是否在
  周圍）。需要多個步驟才能確定的事，由 agent 編排成多次操作與多次判讀。
- 核對的回答是三值：成立／不成立／讀不出。期限內讀不出＝繼續等並
  重讀；期限到仍讀不出＝驗證失敗。
- ［提案］由此得出：領域事實（「(5,3) 有單位」）與畫面空間事實（「螢幕
  點 p 有單位」）之間的換算不在畫面判讀器內。格位 → 螢幕點的投影由持有
  鏡位的 UI sim engine 提供，agent 負責串接。

### 5.3.5 幀的唯一消費者 ［確認］

- 只有畫面判讀器接收畫面輸入。其他物件一律接收結構化參數。
- 畫面判讀器自行決定用幾幀判斷畫面靜止，並提供「阻塞到畫面靜止」的方法。
- ［確認］為了守住 §5.2「等待由主迴圈依期限執行」，阻塞方法的規則：
  1. 期限是參數，由呼叫端（agent）依 UI sim engine 的預期傳入；畫面判讀器
     自己沒有預設的等待秒數。
  2. 回傳值帶等待報告（等了多久、是否收斂），期限到就回傳，不 Halt、
     不重發任何手勢。
  3. 接受「只認 t 之後的幀」參數；t 是手勢送出的時間戳，由操作層回傳。
     這消除 §4.2 第 2 項（幀晚於手勢只能靠 sleep 擔保）。
- ［提案］每個解釋都附帶它所依據的幀識別（時間戳或序號），流水帳存幀
  也走畫面判讀器；證據鏈由此對得上。
- ［提案］推鏡位移在這裡量：阻塞到靜止的同時逐幀累加位移，回傳總位移。
  §4.3 第 1 項的假說在這個方法上驗證。
- 畫面判讀器不持有領域狀態；至多持有一個有界的近期幀緩衝。

### 5.3.6 操作層與危險帶 ［確認］

- 操作物件只做一件事：把一個手勢打到裝置上，回傳送出的時間戳。它不看
  畫面。
- 危險帶由另一個物件管理，按畫面定義（哪個畫面下哪些區域不可點）。agent
  取得當前畫面的危險帶後，注入操作物件；操作物件只對注入的帶做檢查。
- 解鎖檢查改為 agent 的一條規則：畫面判讀器核對「是鎖定畫面」，成立就
  由操作搜尋給出解鎖的手勢。操作物件不再每 30 秒自行檢查。
- ［提案］注入的時機在 §5.1 第 3 步之後：先核對畫面仍是預期的畫面，再
  注入該畫面的帶，再送手勢。帶因此永遠對應到剛核對過的畫面。
- 由此消除 §4.2 第 3 項：帶按畫面定義，不同畫面的鈕不再重疊在同一張
  座標黑名單上，也不需要 intent 豁免。

### 5.3.7 手勢的時間戳與週期粒度

- ［確認］操作物件回傳兩個時間戳：送出開始 t0 與命令返回 t1。t1 由實作
  的命令返回時取得，不限定 adb；換成 scrcpy 控制通道或其他通道時定義
  不變。tap 的兩者
  幾乎相同；swipe 的 t1 − t0 ≈ 持續時間。用途分開：
  - 畫面判讀器「只認 t 之後的幀」用 t0：swipe 進行中的幀也要納入，位移
    累加從手勢開始就要算。
  - 驗證期限從 t1 起算：命令還沒返回之前不可能看到最終結果。
  - t1 只代表命令返回，不代表觸控已送達；「有沒有生效」仍由判讀回答。
- 「一個週期一次操作」對取樣間隔的分析（2026-09-22）：
  - 規則的目的是「操作內沒有觀測」，不是「手勢內沒有時序」。需要毫秒級
    配合的多點觸控做成一個複合手勢，由裝置層執行。
  - 目前已知的遊戲流程沒有需要在兩次觀測之間以短於一個週期的間隔連點的
    情境（應戰窗無逾時；隱藏關彈窗逾時 15 秒，遠大於週期）。
  - 週期的成本＝取幀＋判讀＋手勢，串流取幀 11 毫秒，主要成本在等靜止。
    連續多個不需要驗證的手勢（例如連關三個已知對話框）仍然一個週期一個，
    代價是每個多付一次靜止判斷。
  - 若日後出現需要更短間隔的情境，處置是定義新的複合手勢，不是在操作
    邏輯裡加迴圈。

### 5.4 驗證結果的三分類 ［確認］

- (a) 落在預期集合內：把分支回報給建模引擎。
- (b) 不在集合內但認得出 UI 狀態：以判讀結果覆寫 UI sim engine 的狀態，
  下一週期規則表重新判斷。沒有重試、沒有回退。
- (c) 認不出：停手並留存證據。

### 5.5 觀察引擎與 battle engine 的選擇 ［確認］

- UI sim engine 在進入關卡時讀到關卡名稱，用它查該關卡的資料是否已
  建立在系統中。
- 進入關卡**之前**就確定是否要載入觀察引擎。有觀察引擎＝該關卡沒有
  建檔。
- 「關卡資料已建立」的格式與完整度判準屬於 #92 的範圍，不在此決定。

### 5.6 隊伍暫存與「出擊順位 → 格位」 ［確認］

- 有一個封裝的決策邏輯：透過 UI sim engine 選擇要進入的關卡，並把進入
  關卡的單位資訊暫存。
- 掛觀察引擎時，用暫存的隊伍資料比對地圖上的位置，讓觀察引擎得知隊伍
  內容的哪個順位對應到哪個地圖格位。
- 依 §3：部署位置每次相同、駕駛員唯一，所以這個對應建立一次即可寫入
  關卡資料。
- ［確認］「這一格是哪一台」的取得方式是多個週期的編排，不是單一幀的
  判讀：
  1. 點到一個單位，agent 不認識它。
  2. 經 UI sim engine 與操作搜尋得知：進入單位詳情可以取得單位資料。
  3. 執行；下一週期畫面判讀器讀取詳情頁的資料，整理成結構化格式交給
     agent。
  4. agent 整理成觀察引擎需要的形式，輸入觀察引擎。
  這是 §5.3.4「當前幀答不出的事由 agent 編排」的實例。
- 比對用哪個欄位（駕駛員名、機體名、或 HP／EN 組合）是畫面判讀器與
  詳情頁讀取的實作細節，不在本輪規劃決定。相關：#39；坑冊第 14 條禁止
  用縮圖判定身分。

### 5.7 養成與階段目標 ［確認］

資料現況：成長（等級曲線、突破、SP／SSP）有數據；成長所需的消耗沒有
數據，目前無法建模。這是未來需求，慢慢處理。

三個階段，後一階段建立在前一階段之上：

| 階段 | 目標 | 人提供什麼 | 系統做什麼 |
|---|---|---|---|
| 1 | 自動完成關卡 | 目標關卡、（可選）隊伍 | 進場、觀察或戰鬥、離場 |
| 2 | 可完成關卡的隊伍清單 | 目標關卡 | 用全部數據與 battle engine 搜尋出幾個能通關的隊伍 |
| 3 | 用有限資源拼湊清單內的隊伍 | 目標關卡 | 依持有資源評估可以投資哪個組成；或搜尋最少步驟（要刷哪些關籌集資源）湊出清單內的一支隊伍 |

- 階段 3 的「最少步驟」是另一個搜尋：狀態＝持有資源，動作＝刷某關或
  投資某台，目標＝清單內任一支隊伍成立。它需要消耗數據，目前沒有。
- 對本輪規劃的影響：
  - agent 規則表最上層的目標在階段 1 是「目標關卡已通關」，由人指定
    關卡。
  - 養成這一列在階段 1 只有建模（算 holding 的當前數值給 battle engine），
    沒有評分與搜尋。
  - 隊伍那一列（§5.3.2）在階段 1 可以由人指定隊伍跳過；階段 2 才需要。
- 物件劃分不因階段而改：階段 2、3 加的是新的搜尋與新的資料，不改主迴圈、
  UI sim engine、畫面判讀器。

### 5.9 操作搜尋與 UI sim engine 的查詢合約 ［確認方向］

- ［確認］GOAP 只是搜尋的一種實作。要制定的是 UI sim engine 的查詢合約，
  合約要相容於 GOAP 實作，但不限制只能用 GOAP。
- ［確認］UI sim engine 提供的查詢：當前畫面可以接著到哪些畫面；哪些
  畫面可以進入當前畫面；從某個畫面開始，每一次切換的驗證方法。
- ［提案］查詢合約的具體條目：
  1. `successors(state)` → 每個可做的具名操作，附：手勢、預期結果集合、
     期限、成本。這就是 GOAP 的 operator 展開，BFS／Dijkstra 用的也是它。
  2. `predecessors(screen)` → 哪些（畫面、操作）進得來。供反向搜尋。
  3. `expect(state, operation)` → 預期結果集合＋期限。§5.1 第 4 步的
     驗證依據；與 1 的附帶資料同源。
  4. `project(state, cell)` → 該格在螢幕上的點，或「不在可點區」。地圖層
     用；也是 §5.3.4 領域事實 → 畫面事實換算的入口。
  5. `sync(state)` ／ `advance(state, outcome)`：§5.8 的指定狀態與推進。
- ［提案］戰鬥地圖上的推鏡與點格也走 1：hub 態的 successors 包含
  「朝某方向推鏡一把」（預期＝鏡位改變約 gain × 行程、帶容差）與「點
  螢幕某點」。這樣離散畫面與地圖鏡位是同一個 successors 函式，搜尋演算
  法不必分兩層；先前提的「離散層＋地圖層貪婪一步」只是搜尋實作的一種。
- ［提案］若搜尋實作需要整張圖（例如預先算最短路徑表），由 UI sim engine
  另外提供 graph 匯出合約，內容是 1 與 2 的靜態部分（不含鏡位）。

### 5.10 探索點格的流程 ［確認］

點一個格子做探索，與 UI 流程的搜尋無關；是觀察引擎、畫面判讀器、操作
物件的串接：

1. 觀察引擎（的搜尋）給出要點的格子。
2. 畫面判讀器核對指紋沒變，並給出該格要點的畫面座標。
3. 交給操作物件送出。

- ［提案，待確認］第 2 步「格 → 畫面座標」需要兩樣東西：這一幀的格線
  （畫面事實，畫面判讀器讀）與世界原點相對於螢幕的鏡位（§5.2 已確認由
  UI sim engine 持有）。畫面判讀器不認識「格 (12,7)」；換算由 agent 拿
  UI sim engine 的鏡位加畫面判讀器的格線完成，即 §5.9 第 4 條 `project`。
- ［提案，待確認］點格之後的預期集合｛填色、出卡、選擇態置中｝與期限
  仍由 UI sim engine 的 `expect` 提供，不因格上是誰而縮小。三種結果對
  探索都是合法分支，落在哪一支就是取得的資訊；置中那一支還會改變鏡位，
  由 `advance` 更新。若這份預期不放在 UI sim engine，就會落到 agent
  裡，重蹈 §4.4 第 1 項。
