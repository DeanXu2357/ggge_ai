## 分層

- **外層 HTN**：戰略資源控管——關卡選擇、隊伍編輯、隊員養成、
  強化開發、刷關排程，以及所有關卡外的 UI 操作。
- **內層 GOAP**：進入關卡後的一切——關卡資訊畫面、出擊準備、戰鬥、
  直到終局畫面。以交付給它的本關目標集合為 goal 做符號規劃，
  以「計畫短、驗證勤、發散即重規劃」應對敵方 AI 的不確定性。
  按厚內層設計：未知事件、replan 紀律、情報記錄是一級公民，
  不賭沙盤與搜尋完善後內層變薄的理想情況。
- **層界**：進入關卡那一刻交棒內層；失敗畫面或成功結算畫面出現時
  交還外層。結算流程（領取掉落、返回關卡列表）由外層收尾——
  結算畫面顯示的資源增減正是外層帳本的權威輸入。

選型依據：兩層面對的世界性質不同。關卡外沒有對手，狀態只因自身
操作而變，做法是已知配方——HTN 方法分解的形狀；「不夠強→刷→
強化→再戰」是帶前置條件的候選方法清單。關卡內有敵方 AI，狀態在
控制之外改變，每關條件不同——目標導向加重規劃的形狀。前一版把
多場戰鬥組成的資源迴圈壓進單一 GOAP 符號空間，goal 疊算與
replan 風暴是形式主義錯配的症狀，此為分層的直接教訓。

## 中央迴圈

嘗試 → 情報 → 重估 → 補強或再戰。

- 不設獨立的偵察方法：每次攻略都認真把關卡邊界探測出來，
  planner 在不完整情報下盡力取勝，情報是副產品。
- 關卡失敗不消耗體力與資源（遊戲機制），嘗試本身近乎免費。
- 部分成功（觸發過關條件但 goal 未全達）可由內層主動離開關卡
  避免；若仍過關而 goal 未全達，由外層續策（如再次進入）。
- 情報與資本、素材同為會累積的資產：內層生產、外層消費。
  既有裁決不變：定義檔只當先驗、出擊格永不 cache、畫面才是權威。

## 戰局沙盤（sandbox）與其上的搜尋（expectiminimax）

沙盤（現存實作 `sandbox/model.py`）的定位是關卡內戰局的自營模擬沙盤：程式對「操作中的手機裡
正在發生什麼」的腦內模型，收錄的是不會變更的遊戲規則（傷害公式、
交戰結算順序）。expectiminimax 是沙盤之上的搜尋器。兩者獨立
可注入，兩個使用時機：

1. **外層——診斷式評估**：輸出不只勝率，還有瓶頸類型與缺口數值。
   外層以此做參數微調實驗：擾動隊伍參數、重跑評估，反推出達到
   可接受勝率的最低強化基礎要求，再把要求清單轉成行動規劃
   （刷什麼、強化誰）。
2. **內層——戰術定價**：選機站位、交戰選擇、應戰姿態。
   確定性效果模型與隨機戰鬥的相容靠保守下界：計畫只承諾保證得了
   的事（forecast 為下界、KILL 才算確定擊殺），多賺的由重規劃收割。

沙盤不得依賴即時感知型別：兩個使用端各自從自己的來源
（情報快取／即時戰場狀態）組裝沙盤輸入。

## goal 規格

使用者指定的 goal ＝ 關卡 ＋ 目標項目子集 ＋ 達成約束。
內層只對交付給它的「本輪目標集」負責；整體 goal 是否達成由
外層判斷與續策。

目標項目四種：

- **過關（clear）**：滿足該關勝利條件。勝利條件是參數——擊破
  特定目標／指定或任意單位到達指定地點／全滅敵人——來源為關卡
  info 畫面，參數化內層 goal 與沙盤評估。判定權威：結算畫面與
  關卡列表狀態（遊戲判定為準）。
- **評分過關（score）**：結算評分 10000，僅限有評分的關卡。
  判定權威：結算畫面（外層親讀）。工具價值：解鎖略過——刷資源
  從整場戰鬥變成直接消耗體力換資源（每日次數上限），因此
  「把刷關目標關卡打到評分門檻」可由外層自主生成為資源規劃的
  前置子目標。主線無公開公式；操作先驗＝10 機全存活＋每機殘
  HP > 50%（待實測，詳 docs/reference/rewards-and-scoring.md）。
- **成就（achievement）**：以特殊條件完成關卡，對應永恆之路
  （Eternal Road）關卡的逐關任務。判定權威：永恆之路任務清單
  畫面（關卡外 UI，外層查驗）。
- **隱藏關卡（hidden）**：達成 info 記載的特殊條件後出現觸發
  彈窗（15 秒逾時、一輪一次），選擇進入並完成戰鬥。錯過只能
  重打；下輪重新達成條件會再出現。進入可能犧牲本輪評價。

達成約束——goal 必須明示範圍與是否須同輪同時成立：

- **分輪達成**：允許外層把目標項目拆成多次進場（如 hidden 與
  score 衝突時分開跑）；為取得資源多次完成同一關的不同要求
  也屬此類。規劃自由度最大。
- **單輪全成**：一次進場同時達成全部指定項目的極限操作規劃。

派工含義：外層每次派內層進場附本輪目標集，內含觸發彈窗的既定
方針（進／不進）——15 秒逾時內層沒有上報等指示的餘裕，方針
必須在派工時定好；這同時是內層迴圈「感知＋決策＋操作」節奏的
硬上限。

## 資源帳本

外層世界狀態是持久帳本：開機同步一次（或載入 cache），此後只由
自身動作的效果更新——沒有外部事件會動資源。出擊與強化畫面顯示的
數字當一致性探針：對不上即斷開、保留狀態，下次從同步重來。

## 需求對應

- 需求 1（指定與完成）：HTN 根任務。
- 需求 2（戰鬥自主）：內層全權決策；以硬閘門攔截遊戲內建 AUTO。
- 需求 3（資源控管）：HTN 方法選擇＋資源帳本＋診斷實驗迴圈。
- 需求 4（遵守關卡條件）：本關目標集合參數化內層 goal。
- 需求 5（誠實停止）：結構性觸發——HTN 無適用方法、內層卡死上拋、
  帳本一致性探針分歧。不靠計數器猜。
- 需求 6（過程可查驗）：兩層共用流水帳紀律，jsonl＋逐 tick 原生
  截圖同 run 目錄保存（幀檔名入流水帳供歸因）；舊 run 壓縮輪替、
  只留最新未壓縮。

## 事實依據的邊界

新規劃只站在兩種事實上：

- `docs/requirements/base.md` 的需求。
- 不會變更的遊戲與裝置事實：戰鬥公式與交戰結算順序
  （`docs/reference/combat-formulas.md`，實機觀察定案）、實機標定的
  UI 座標與模板、裝置解析度與 adb 操作方式。

既有程式碼一律只是實作參考：可查閱、可借用部分邏輯，但過去的
處理流程與架構安排（`agent/`＋`domain/` 舊雙層，以及各模組的
流程）不作為推斷依據，新規劃不遷就既有實作。

## 待辦與待設計

1. goal 輸入介面：使用者指定目標項目與達成約束的具體形式。
2. 瓶頸分類法與缺口量綱：診斷輸出的型別設計。
3. 參數微調實驗迴圈：擾動維度、評估預算、收斂判準。
4. 內層回報物件欄位：終局種類（勝／敗／卡死／主動離開）、
   本輪目標集達成情況、情報增量、結算摘要的歸屬（外層親讀
   結算畫面）。
5. 內層行動詞彙：主動離開關卡、隱藏關卡條件推進與觸發彈窗
   方針執行如何入 catalog。
6. 內層迴圈的執行紀律（截圖與互動的節奏、佇列推進、反射與熔斷、
   流水帳格式；15 秒觸發彈窗為節奏硬上限）：設計期自行推導定案，
   不繼承舊版流程。
7. 評分假設實測：10 機全存活＋每機殘 HP > 50% 通關是否得 ★3
   （批 2 順手驗；結算樣本照蒐供反推）。
